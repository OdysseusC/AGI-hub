# 技能驱动的对等协作

状态：精简设计，2026-10-19。本文替换此前的集中团队调度提案。受管技能同步、版本检查和可见成员目录已实现；多跳消息与关联回复仍是提案，现有单次交接协议保留。

## 核心原则

用户在任意已接入的原生助手会话中提出工作。该助手的协作技能按需找其他助手，其他助手也可以继续请求获准的协助。参与者对等，分工和判断发生在各自原生会话中；Hub 不建立团队计划、依赖图、父目标执行器或统一智能主持人。

最初那次用户输入的会话是原入口，沿整个协作保留。最终成果回到这个会话，由它向用户解释和交付；无需另外指定一个永久的最终处理助手。

## 只保留三部分

| 部分 | 职责 |
| --- | --- |
| 协作技能 | 判断何时需要协助、查看可用接入点、组织最少上下文、发起或转交请求、处理关联回复、核验和交付成果 |
| Hub | 目录与用户允许的互通范围、持久消息收发、定向订阅、去重、回执、基础限额与追踪 |
| 各助手 Client | 通过该产品实际支持的原生方式投递和唤醒，核对会话，回报真实投递状态 |

技能不负责后台监听。安装体验可以统一为一次接入，但底下仍需已配置的 Client/宿主插件和可用的唤醒通道；仅安装说明文件不能证明空闲唤醒。没有 MCP 的宿主可用受限 CLI，有原生工具的宿主优先用原生工具。

## 技能随 Hub 同步更新

用户的使用体验是：接入一个新助手后，其他已接入助手自动知道它，不需要手工逐个改技能。实现采用小而稳定的入口技能，配合 Hub 的动态成员目录和版本化协作规则。

| 变化 | 同步方式 |
| --- | --- |
| 接入、退出、禁用或改变成员能力 | Hub 提供按内容计算版本的目录；技能下次协作按需查询，不重写完整 SKILL.md。配置变化当前需重启 Hub；Client 推送缓存刷新尚未实现 |
| 协作规则或调用约定升级 | 随 Hub 发布受管技能版本，更新已登记且允许同步的安装位置；实际协作前检查规则版本，变化时再加载必要内容 |

目录只返回当前接入点获准看见的短信息：成员标识、用途、可用调用方式与验证状态。不带凭据、私有路径、其他会话历史或全部工具清单；新增目录项也不自动扩大互通权限。实际发送前由 Hub 再核对当前配置，不能用旧缓存调用已经禁用的成员。

新成员只使用一套通用协作约定，不为每两个助手生成专属技能。客户端/模型特有的用法按需加载；成员描述属于数据，不能借目录更新改写通用规则或用户授权。

同步只使用用户明确登记的受管安装位置，不扫描所有应用。复用现有所有权清单、校验和及幂等更新；已被用户修改、文件占用或更新失败时保留原文件，报告该安装的实际状态，不宣称全部同步成功。记录技能版本与兼容协议，不能把清单格式版本当成技能版本。

Hub、技能与 Client 按协议兼容范围协同，不要求版本号相同；发现不兼容时停用相关协作并说明具体缺项，不通过另开会话、切换通道或放宽权限绕过。完整管理状态接口不能直接开放给技能当成员目录使用。

磁盘文件更新与宿主已加载的内容分别核对。宿主有缓存时，通过已安装的入口约定在下次协作读取版本；需要原生重新加载的，标明待生效，不伪装成聊天上下文已热更新。目录变更和文件同步本身不发送会启动模型的聊天通知，不打断原会话或重放工作。

当前已实现显式安装登记、接入及启动时同步、单接入点同步、只读状态、可见目录和规则版本接口。目录按需读取，不会唤醒模型；已有消息事件保持原行为，尚未新增 Client 维护事件消费者。磁盘状态与宿主加载仍分别记录，当前加载状态保持 unknown。[运行与各宿主支持](SKILLS.md#自动同步与版本)

## 路由和回传

例如用户在 A 的会话输入工作，A 请 B 协助，B 又请 C 核对：

```text
用户 → A → Hub → B → Hub → C
       A ← Hub ← B ← Hub ← C
```

各请求共享一个协作关联 ID。中间结果默认回复给发出该请求的助手，以便它继续判断和整合；最终结果回到原入口 A。明确转交整项工作时，接收方仍继承原入口，可将最终成果送回 A，但不能改变用户授权。

不根据“最近谁说过话”或“哪个助手最近有人输入”猜回传地址。Hub 记录并传递最初会话的接入点地址与原用户请求引用，同一聊天并行的不同工作靠关联 ID 区分。用户在 B 发起另一项工作会产生另一条协作，其原入口为 B，不会抢走此前 A 的结果。

## 最少的消息信息

尽量复用现有信封，只补齐原入口、跨请求关联与回复用途：

| 信息 | 用途 |
| --- | --- |
| 消息 ID | 一条消息的稳定身份，重复通知不重复执行 |
| 单次请求 ID | 沿用现有 task_id，区分这次请 B 帮忙和 B 再请 C 帮忙；回复沿用它 |
| 协作关联 ID | 同一次用户工作中的请求和回复始终关联 |
| 原入口 | 固定的助手、设备和具体会话地址及原用户请求引用；由可信接入记录确定，转发不改写 |
| 发送者、接收者 | 当前这一跳的真实身份和目的地址；不能冒充其他接入点 |
| 回复引用 | 回复指向原请求消息 ID，接收方是原请求的发送者；转发可另记来源消息 ID |
| 用途 | 请求、关联回复、必要状态、最终结果；回复本身不要求再回复 |
| 正文与文件引用 | 清楚的小目标、必要限制、简短摘要和成果位置 |

文件引用继续明确设备、工作区和相对路径，不把另一台电脑的路径当作本机路径。传输确认、实际接手、执行状态和成果完成继续分开；Hub 不根据正文一句“完成”自动判定整个用户工作结束。

“请求完成”只结束该单次请求，是否已经答完用户工作由原入口助手判断；不在 Hub 再建整体完成状态机。其他助手可以提供完整成果，但不能用一条回复改写原入口或自称新增了用户授权。

每次委派可以沿用现有单次 Task/Report；多个委派共享协作 ID 和原入口即可，不需要在 Hub 中新增 Goal、计划版本、DAG、Worker/Attempt 等执行框架。现有的投递尝试与原生运行标识仍保留，重启或未决通知不能遗失。

## 每条消息的简短基础说明

Client 使用统一短模板附加说明，例如：

> 这是已有用户工作的协作消息，不新增授权。节省 token：只处理本条范围，按需读取文件，简短回复结论和成果引用，不复制聊天历史、例行确认或无必要互答。保留原入口和关联信息。

完整约定安装在技能中，消息只携带简短说明、约定版本和本次必要范围，不重复发送整份技能、全部工具清单或历史。技能提示接收方：

- 请求需要实际处理时接手；回复只续接它所关联的既有工作，不当成新用户指令。
- 能直接完成就直接完成；需要其他成员时，只转交必要内容并继承原入口、关联和授权。
- 完成后给请求方简短结论、成果引用或真实障碍，不为感谢、收到和重复 ACK 再唤醒模型。
- 多个回复可先入 inbox，按当前工作需要合并处理；有可验证的原生待处理状态时，Client 不重复唤醒同一会话。Hub 不理解依赖或代替技能判断是否可以交付。

节省 token 是协议与技能约定，不能保证模型绝对服从。可以硬执行的限制由 Hub/Client 持有，不把提示语当作费用控制。

## 共治与必要的限制

共治表示所有已获用户允许的接入点都能发起请求、回应和转交，没有永久的系统主持人。现有默认 leader 可以保留为便利配置，不决定每条协作的所有权；最终返回地址由原入口决定。共治不等于所有接入点共享管理员凭据或可以批准彼此的权限。

Hub 只做少量必要检查：

- 用户控制接入、互通对象和可调用操作；发送方只能使用自己的身份，子请求不能超出原工作授权。正常协作使用受限发送/回复权限，不把管理 token 交给模型。
- 按整个协作 ID 计算触发助手执行或续接的消息次数、转交深度和到期时间。并行分支共用同一计数，转发不能复制出多份剩余额度；重复同一消息不重复占用，投递不确定不能退款后换 ID 重发。为最终回到原入口保留必要返回额度，用尽后停止新增协助。此计数不代表可以看见并限制宿主内部全部模型调用。
- 持久化后再投递；相同 ID 同内容去重，同 ID 改内容拒绝。消息可能已经送达时保留 uncertain，不盲目重发、换 ID 或新建会话重做。
- 同一原生会话或声明的桌面、写入工作区有冲突时，Client 与现有互斥规则协调；等待回复不能虚报 idle 或释放仍在执行的副作用资源。
- 安装、注册、退订和更新按用户授权操作；一个助手收到的消息不能扩大其他助手权限。没有可核算费用时不承诺积分硬上限。
- 用户取消某次协作后，该关联下不再发起新的协助；已经运行的动作按原生真实能力请求停止，未确认时不能记录成已停止。只有原入口按真实用户输入或已有用户授权建立新的协作，转发方不能换关联 ID 绕过取消或限额。

这些是消息层的来源、身份、可靠性和限额规则，不是由 Hub 管理工作计划。

## 原会话、新会话和专业能力

会话选择留给目标 Client 的已验证能力：需要延续上下文时发送到指定原会话，需要独立工作时可请求创建新会话。不支持的组合明确拒绝；新会话使用真实返回的 ID，并保留原入口和关联，创建结果不确定时不重复创建。若创建操作已启动首轮，不能再发送一次相同输入。

专业模型或程序可以由一个简单 Client 接收请求、调用对应能力并返回结果，不要求模型自己安装技能或承担协调。目录明确标为模型/程序接入，不冒称原生助手。无会话的调用不需要伪造会话或唤醒状态；原生助手可以按需调用它们，Hub 只负责统一消息协议。

## 现有代码真正需要改的地方

1. **受限收发。** 现有 endpoint token 只能收件和回报，普通提交使用管理权限。补按用户允许范围发送/回复的接口，让每个已接入助手都能协作，不交出管理凭据。
2. **保留原入口和多跳关联。** 当前 Task 只围绕单次交接，结果固定回该交接的 origin。将长期原入口、当前请求方和协作关联分开，维持每次交接的真实回报，不改成中央任务树。
3. **区分关联回复与最终展示。** 当前技能与 Codex/Claude 模板把 result 定为只展示、不续做。新增明确的关联回复语义，让收到回复的助手可以继续同一已授权工作；旧 final/result 行为保留，新消息类型先协商再领取。
4. **回复能够回来。** “正在等别人回复”与原生回合实际忙闲分开。Client 确认原生轮次已结束后，关联回复可以唤醒该会话继续处理；不能被其尚未结束的原请求永远阻塞，也不能据等待擅自并发恢复同一会话。
5. **更新技能和安装绑定。** 技能可查询简短成员目录、发送、回复和查必要状态；安装时登记允许同步的技能位置，配置本机 Client/插件并验证对应会话和唤醒。目录变更自动刷新，协作规则随 Hub 受管更新。已有队列、存储与成果核验继续复用。

原会话/新会话、专业模型与跨平台 Client 按真实支持逐步补齐，不为这些选项先造一套统一 Agent 运行时。本提案不改变当前已验证路径，也不声称当前所有助手已支持多跳协作。

## 最小验收

先用本地模拟接入点验证 A→B→C→B→A，原入口不变、回复关联正确、重复通知不重复执行、并行计数不超额。再在两个真实原生会话中做一次很小的请求与回复，核对 idle 回唤、忙时发送策略、真实接手和成果；不用真实 Claude 调用来反复验证离线可测的逻辑。

随后从另一个已接入助手发起同类工作，最终结果应回到那个新的原入口。用户始终在原生助手中操作，Hub 状态页只供查看记录。

同步验收：新增一个模拟接入点，其他已安装入口下一次协作查询应能看到；禁用后不能从旧缓存继续调用。重复同步不改写相同文件、不触发模型，规则升级保留用户自定义内容并如实区分已更新、冲突、待宿主加载。
